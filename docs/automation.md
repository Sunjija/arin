# 한사코치 자동화 운영

## 구현 순서
1. 독립 브랜치에서 Actions와 검사 스크립트를 추가한다. 제품 기능·의존성·사용자 기록은 변경하지 않는다.
2. 감사 규칙 자체 테스트와 콘텐츠 보고서를 로컬에서 확인한다.
3. 자동화 브랜치 push로 GitHub 실행을 확인한다. 기존 앱 오류와 자동화 설치 오류를 구분한다.
4. 자동화 파일만 main에 반영한다. 이후 main 대상 PR 열기/수정 및 main/codex/cursor/work 브랜치 push에서 실행된다. 기존 PR은 다음 변경·재개 시 검사한다.
5. Codex의 현재 작업에 매일 오전 9시(Asia/Seoul) 정기 점검을 연결한다. 금요일에는 공식 시험 일정도 확인한다.

## 자동 실행 결과
GitHub PR의 Checks 또는 Actions → Hansacoach quality에서 단계별 상태를 확인한다. Summary는 단원별 콘텐츠 수와 변경 영향 검토 목록이며, Artifacts의 audit.json에는 상세 경고와 기준 SHA가 있다. 보관 기간은 14일이다.

실행: npm ci → 감사 규칙 테스트 → 콘텐츠/변경 영향 → 타입 → lint → 회귀 테스트 → 빌드. 한 검사 실패로 다른 검사를 숨기지 않으며 실패는 전체 상태에도 남는다. npm 잠금파일을 기준으로 설치한다.

로컬 재실행:
```bash
node --test scripts/automation/audit.test.mjs
node scripts/automation/audit.mjs
```
생성된 automation-reports는 커밋하지 않는다.

## 자동 검수의 한계
- 규칙 검사: 중복 ID·잘못된 정답/선지·단원 시대 불일치 차단. 단원 매핑/출처 누락은 보충 목록으로 보고한다.
- TypeScript AST로 리터럴 데이터만 읽으며 소스를 실행하지 않는다. 데이터 구조가 동적/분리 은행으로 바뀌면 어댑터를 수정해야 한다. 미지원 구조는 실패시켜 조용히 잘못 집계하지 않는다.
- PR 변경 경로로 공유 계약·콘텐츠·문서 검토 대상을 제안한다. 문서 수정 누락은 휴리스틱이며 완전한 정책 준수 검증이 아니다.
- 문항 역사적 사실·정답 유일성·변별력·이미지 권리 승인은 사람/근거 자료 검수가 필요하다.
- 기존 브랜치의 실패를 검사 우회로 숨기지 않는다. 보고서와 기존 코드 결함을 구분한다.

## 정기 에이전트 점검
매일 새/변경 PR, CI 실패, 기록 손실·학습 정책·문서 불일치·콘텐츠 공백을 검토한다. 금요일에는 공식 일정 변경을 확인한다. 처음은 기준 상태를 기록하고 이후 변경/조치 필요 상황만 알린다. 같은 문제를 매일 반복 통지하지 않는다.
Codex 자동화의 실행 환경·연결 상태가 필요하며 GitHub CI와 별개다. 자동화 UI에서 비활성화/주기 변경이 가능하다. API 키나 유료 AI 워크플로를 GitHub에 추가하지 않았다.

## 권한과 운영
Actions는 contents:read만 사용하며 PR 댓글 작성·자동 병합·배포·콘텐츠 발행은 하지 않는다. fork PR은 저장소 설정에 따라 첫 실행 승인이 필요할 수 있다. 이 설정은 브랜치 보호를 자동 변경하지 않는다.
수정 후 PR 작성 → 자동 결과 확인 → Cursor가 실패/누락 수정 → 총괄이 설계·콘텐츠 검수 → 승인된 병합·배포 순서로 운영한다.
